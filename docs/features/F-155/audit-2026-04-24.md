## 3. Divergences identifiées

### D1 — [visuelle] Formatage dates dans les résultats (ISO brut vs pipe `date`)

**Composants concernés** : `oqtf-avec-delai-section` (affiche `{{ result()!.dateExpirationDdv }}` brut ISO), `annexe13-be-section` (idem ISO brut) versus `oqtf-sans-delai-section` (utilise `| date:'dd/MM/yyyy HH:mm'`).
**Impact** : visuel — l'utilisateur voit `2026-05-01` dans oqtf-avec-delai/annexe13 alors qu'il voit `01/05/2026 10:00` dans oqtf-sans-delai. Divergence de lisibilité pour l'avocat FR.
**Reco harmonisation** : appliquer systématiquement `| date:'dd/MM/yyyy'` pour toute date ISO affichée dans les templates de résultat. Créer un pipe partagé `displayDate` si nécessaire.
**Estimation migration** : ~1h (éditer 2 templates + mettre à jour tests snapshot).

### D2 — [comportementale] Affichage `formule` dans le bloc résultat

**Composants concernés** : `harcelement-licenciement-nul` / `inaptitude` / `heures-sup` affichent `result()!.formule` en span JetBrains Mono sous le montant. `oqtf-avec-delai` / `oqtf-sans-delai` / `annexe13-be` retournent `formule` dans la DTO mais ne l'affichent PAS dans le template — seul `baseJuridique` est affiché.
**Impact** : comportemental — l'avocat ne voit pas le calcul dans les 3 outils "statut délai" alors qu'il le voit dans les 3 outils "calcul montant". Fonctionnalité perdue.
**Reco harmonisation** : ajouter un bloc `.XXX-formule` (JetBrains Mono, 13px, secondaire) dans le template résultat des 3 composants statut. Alternative : accepter le choix métier — les outils "statut délai" n'ont pas de formule numérique significative — mais alors supprimer `formule` de la DTO backend pour éviter le champ mort.
**Estimation migration** : ~2h (templates + clarification métier).

### D3 — [visuelle] `list-style` des messages

**Composants concernés** : `harcelement-licenciement-nul` / `inaptitude` / `heures-sup` utilisent `list-style: none` + fond or. `oqtf-avec-delai` / `oqtf-sans-delai` / `annexe13-be` utilisent `list-style: disc inside` + fond or/rouge.
**Impact** : visuel — rendu différent selon l'outil (puces visibles ou non).
**Reco harmonisation** : canonique = `list-style: none` + padding de 8px 12px + fond or semi-transparent (pattern établi par template canonique). Migrer les 3 oqtf/annexe13 à ce pattern.
**Estimation migration** : ~30 min (éditer 3 fichiers .scss).

### D4 — [architecturale] Switch conditionnel inline FR/BE dans `heures-sup-section`

**Composants concernés** : `heures-sup-section` — template contient `@if (workspaceCountry === 'FRANCE') { … FR fields … } @else { … BE fields … }` dans le même form. Les autres country-gated (oqtf-*, annexe13) séparent via composants distincts (pattern "un outil = une situation"). Les dual FR+BE (harcelement, inaptitude) factorisent le champ enum via `computed` sans dupliquer les fields.
**Impact** : architecturale — `heures-sup-section` est à la frontière : soit le scinder (SF-DT-19-02 FR + SF-DT-19-YY BE) pour respecter l'invariant, soit accepter car les règles métier sont à 90 % identiques (heures × taux × majoration). Signalé pour arbitrage.
**Reco harmonisation** : **à arbitrer** avec l'utilisateur. Si scission → créer feature jumelle F-DT-19bis au backlog. Sinon, accepter le switch inline et documenter dans le header de classe `@Component`.
**Estimation migration** : ~0 si on accepte, ~1 jour si on scinde.

### D5 — [visuelle] Couleur de l'icône header

**Composants concernés** : `oqtf-sans-delai-section` — `.oqtf-sd-icon { color: #c02424; }` (rouge). Tous les autres utilisent `color: var(--ds-accent-gold, #c9a54b)`.
**Impact** : visuel — cohérent avec l'exception rouge dominante urgence 48h, mais à documenter comme exception explicite.
**Reco harmonisation** : accepter l'exception (déjà justifiée par l'urgence 48h) et ajouter un commentaire dans la checklist SCSS pour éviter qu'un autre composant copie l'exception sans justification.
**Estimation migration** : ~10 min (commentaire SCSS déjà partiellement présent).

### D6 — [visuelle] Couleur du button submit sur oqtf-sans-delai

**Composants concernés** : `oqtf-sans-delai-section` — `<button mat-flat-button color="warn">`. Tous les autres utilisent `color="primary"`.
**Impact** : visuel — bouton rouge Material cohérent avec l'urgence 48h. Exception justifiée.
**Reco harmonisation** : accepter l'exception. Ajouter dans le template canonique du skill une mention "button color=`primary` par défaut, `warn` autorisé uniquement en complément d'une palette rouge dominante justifiée".
**Estimation migration** : ~5 min (documentation).

### D7 — [comportementale] Couverture des tests spec

**Composants concernés** : `harcelement-licenciement-nul` (8 tests), `inaptitude` (9), `heures-sup` (8). Les 3 sont sous le seuil canonique de 10 tests.
**Impact** : comportemental — couverture moindre des cas limites pour les 3 outils "calcul montant". Risque de régression silencieuse lors de refactors futurs.
**Reco harmonisation** : ajouter pour chaque composant : (a) test `toggleCollapse()`, (b) test `editMode()`, (c) test du flag dashboard refresh, soit +3 tests chacun → cibler 11+.
**Estimation migration** : ~1h par composant (~3h total).

### D8 — [architecturale] Badges additionnels dans le header

**Composants concernés** : `oqtf-sans-delai-section` ajoute `.oqtf-sd-chip--cra` (CRA). `annexe13-be-section` ajoute `.annexe13-badge-transfert` (⚠ TRANSFERT IMMINENT). Pattern similaire (chip contextuel additionnel) mais classes CSS et styles divergents.
**Impact** : architecturale — 2 mécanismes ad-hoc pour le même besoin "signaler un flag critique dans le header". Début de dette de convergence.
**Reco harmonisation** : extraire un composant partagé `<app-decisional-header-flag [label]="…" [severity]="…">` consommable par toutes les sections. Définir 3 severities : `urgent` (or), `critical` (rouge), `info` (navy).
**Estimation migration** : ~3h (créer composant, migrer 2 usages, couvrir par tests).

### D9 — [comportementale] Citation des articles juridiques dans les messages

**Composants concernés** : les 6. Aucun n'utilise `<code>` JetBrains Mono pour citer les articles dans les messages (ex. `'Art. L.1235-3-1 Code du travail'`), alors que le skill §5 l'exige.
**Impact** : visuel + accessibilité — pas de distinction typographique entre le texte courant et la référence juridique, mal scannable.
**Reco harmonisation** : définir un pattern backend : retourner les messages avec syntaxe markdown inline (`"L'indemnité est doublée — `Art. L.1226-14`"`) et un pipe Angular `legalCitations` qui convertit en `<code>`. Alternative : construire un sub-template template-driven.
**Estimation migration** : ~4h (pipe + migration des messages côté backend des 6 outils + test).

### D10 — [visuelle] Formes des chip statut dans le header (`oqtf-avec-delai` vs `annexe13-be`)

**Composants concernés** : `oqtf-avec-delai-section` et `annexe13-be-section` utilisent les mêmes 4 modificateurs de chip (`--danger` / `--warning` / `--success` + défaut navy) avec les mêmes valeurs rgba — confirmation que la convention palette tient. `oqtf-sans-delai-section` utilise 3 modificateurs `--danger-medium` / `--danger-strong` / `--danger-dark` + `--success` + `--cra`.
**Impact** : nul — pattern cohérent. Seule divergence : nomenclature `--danger-*` vs simple `--danger` (liée à palette rouge dominante, justifiée).
**Reco harmonisation** : aucune — noter dans le template canonique que les composants "statut délai" doivent respecter ce schéma.
**Estimation migration** : ~0.
