# Blocages automatiques — règles détaillées

Référencé depuis `CLAUDE.md`. Toute violation déclenche un refus immédiat avec le format de refus standard.

## Format de refus standard

```
REFUS [contexte]
Motif : [raison précise]
Artefact manquant : [ce qui doit être produit]
Référence : [fichier de gouvernance concerné]
```

---

## Tableau complet des blocages

| # | Situation | Réponse |
|---|-----------|---------|
| 1 | Demande brute couvrant plusieurs features distinctes | REFUS — séparer les features avant tout découpage |
| 2 | Demande de code sans mini-spec produite dans la conversation | REFUS — produire la mini-spec d'abord (`subfeature-template.md`) |
| 3 | Demande de code sans critères d'acceptation dans la mini-spec | REFUS — compléter la mini-spec |
| 4 | Demande de code sans plan de test dans la mini-spec | REFUS — compléter la mini-spec |
| 5 | Mini-spec sans section "Analyse de cohérence transversale" remplie | REFUS — scanner les autres outils / pays / domaines / UI patterns d'abord, classer chaque cible applicable (intégrée / SF parallèle / backlog / non applicable avec justification) |
| 6 | SF introduit un composant partagé / service / endpoint transversal / directive / DTO réutilisable sans section "Nouveau pattern UI ou service partagé" remplie | REFUS — scanner toutes les zones où le pattern pourrait être réutilisé (badges, tooltips, popovers, panneaux existants), identifier les patterns concurrents à harmoniser, classer chaque cible (harmonisation immédiate / SF parallèle / backlog / non applicable). Évite la *dette de convergence* (2 mécanismes similaires qui divergent dans le temps). |
| 7 | Feature non découpée en subfeatures | REFUS — demander le découpage (`feature-splitter`) |
| 8 | Subfeature estimée > 2 jours | REFUS — demander un redécoupage |
| 9 | `git push` sans review checklist passée dans la conversation | REFUS — passer la review checklist d'abord |
| 10 | Push sans release checklist produite dans la même réponse | REFUS — release checklist fait partie du même bloc que le push |
| 11 | Démarrage d'une nouvelle subfeature sans release checklist passée pour la précédente | REFUS — produire la release checklist avant de continuer |
| 12 | Merge confirmé sans mise à jour PRODUCT_SPEC.md si feature parente complète | REFUS — mettre à jour PRODUCT_SPEC.md d'abord |
| 13 | Question ouverte non tranchée et bloquante | BLOCAGE — signaler, ne pas avancer |
| 14 | Incohérence avec `ARCHITECTURE_CANONIQUE.md` | BLOCAGE — signaler la divergence |
| 15 | Feature non référencée dans `PRODUCT_SPEC.md` | REFUS — ajouter la feature au PRODUCT_SPEC avant tout dev |
| 16 | Traitement IA demandé de façon synchrone | REFUS — rappeler la règle async |
| 17 | Accès données sans filtre `workspace_id` | REFUS — rappeler la règle d'isolation |
| 18 | Composant frontend utilisant couleurs/polices hors `DESIGN_SYSTEM.md` | BLOCAGE — signaler la divergence |
| 19 | Écran produit sans header/layout conforme au design system | BLOCAGE — signaler la divergence |
| 20 | Feature avec écran utilisateur marquée `Terminée` sans composant Angular implémenté | REFUS — implémenter les écrans manquants avant de marquer Terminée |
| 21 | Subfeature backend mergée sans subfeature frontend planifiée (si la feature a une UI) | BLOCAGE — planifier et créer la subfeature frontend correspondante avant de continuer |
| 22 | Merge d'une SF frontend qui consomme un endpoint API alors que la SF backend correspondante n'est NI mergée NI dans une PR ouverte avec tests verts | REFUS — la SF frontend ne sera pas utilisable en production sans le backend (404 en runtime). Vérification : (1) lister les endpoints consommés par les services Angular modifiés (`HttpClient.post`/`get`/`put`/`delete` sur `/api/v1/...`), (2) pour chaque endpoint, confirmer qu'une route Spring `@RequestMapping` existe sur master OU sur une PR ouverte mergeable. Si absent : implémenter la SF backend manquante d'abord. Motivation : cas réel F-DT-29 2026-04-25 — SF-DT-29-02 frontend mergée (PR #624) consommait `/api/v1/case-files/{id}/credit-temps-be-analysis` qui n'existait pas. Correctif PR #626 rétroactif. |
| 23 | Migration Liquibase qui INSERT/UPDATE dans `decision_tool_visibility_rules` un `tool_id` absent de `TOOL_REGISTRY` frontend (et de la liste `KNOWN_FRONTEND_TOOL_IDS` du test d'intégrité) | REFUS — l'outil sera silencieusement masqué en runtime (`resolveEntry()` retourne `null`). Vérification : (1) lister les `tool_id` ajoutés/modifiés ; (2) confirmer que chaque ID possède une entrée `TOOL_REGISTRY` dans `frontend/src/app/case-files/decisional-tools-panel/decisional-tools-panel.component.ts` ; (3) mettre à jour `KNOWN_FRONTEND_TOOL_IDS` dans `DecisionToolVisibilityIntegrityIT`. Motivation : cas réel 2026-04-26 — 15 `tool_id` orphelins → panneau F-IA-04 quasi vide en staging. Garde-fou F-164 SF-164-01. |
| 24 | Préoccupation transversale cochée sans liste de composants impactés dans la mini-spec | BLOCAGE — compléter l'analyse d'impact avant de continuer |
| 25 | Smoke tests E2E échouent après implémentation d'une préoccupation transversale | BLOCAGE — corriger avant push |
| 26 | Ajout backlog ou SF touchant un outil décisionnel métier sans scan systématique des autres outils décisionnels | REFUS — scanner tous les outils décisionnels existants, classer chacun (déjà séparé / multi-situations à scinder / paramétrage simple), inclure les cas jumeaux dans le périmètre ou ouvrir des features jumelles au backlog |
| 27 | Mini-spec sans section **"Impact par domaine métier"** remplie | REFUS — pour chaque SF, répondre explicitement : cette feature est-elle sensible au domaine (droit du travail / immigration / famille) ? Si oui, comment elle se comporte sur les 3 — et sur les 2 pays (FR + BE) quand pertinent. Si transversale, le dire explicitement. Motivation : cas réel F-145 SF-145-01 — enum `DocumentPieceType` initial adapté uniquement droit du travail, correction via SF-145-09. |
| 28 | SF livre un outil décisionnel de **niveau ≥ 5** (scoring / comparateur / détection d'événement) sans section **"Parité des domaines métier"** remplie | REFUS — à chaque scoring (niveau 5), comparateur (niveau 6) ou détection d'événement déclencheur (niveau 7) livré pour un domaine, lister explicitement si les 2 autres domaines ont l'équivalent. Si non : ouvrir une feature jumelle au backlog avec numéro dédié, ou justifier. Motivation : F-DT-08/09/10 livrées pour droit du travail seul, laissant Famille et Immigration 3 niveaux en retard — corrigé via F-150 à F-153. Les 7 niveaux de profondeur : (1) Checklist, (2) Générateur de document, (3) Calculateur, (4) Arbre décisionnel, (5) Scoring / analyse validité, (6) Comparateur / fourchettes, (7) Détection événement déclencheur. |
| 29 | Migration Liquibase qui INSERT une entry `legal_referentials` avec `is_system=true` sans la colonne `description` renseignée | REFUS — ajouter `description` (texte en langage avocat). Seuls les 7 types à description riche native dans `value_json` (`LICENCIEMENT_CRITERES`, `RUPTURE_CONV_CRITERES`, `IMMIGRATION_TITLES`, `IMMIGRATION_RECOURS`, `IMMIGRATION_WORK_RIGHTS`, `DIVORCE_ETAPES`, `DIVORCE_PIECES`) en sont exemptés. Le test `LegalReferentialDescriptionIntegrityIT` échoue automatiquement en CI. Garde-fou F-140 SF-140-03. |
| 30 | Modification d'un référentiel métier statique (classe `*Referentiel.java`) **sans migration Liquibase accompagnant l'INSERT/UPDATE dans `legal_referentials`** | REFUS — la classe Java statique n'est qu'un **fallback**, la source de vérité est la table `legal_referentials`. Toute nouvelle entrée ajoutée au Java DOIT être accompagnée d'une migration Liquibase correspondante. Divergence Java vs DB = bug silencieux en prod où la DB prime. Cas historique F-IM-01 SF-IM-01-04 2026-04-23 : 9 nouveaux types ajoutés en Java uniquement, rattrapé via migration 101. |
| 31 | Migration Liquibase qui INSERT un nouveau `referential_type` dans `legal_referentials` (`is_system=true`) **sans intégration UX dédiée côté frontend** | REFUS — l'écran "Guide & Barème" affichera un titre brut et une valeur en `JSON.stringify`. Vérification : (1) label humain dans `SECTION_LABELS` ; (2) `formatValue()` pour rendu lisible ; (3) `sectionIcon()` avec icône MatIcon ; (4) éventuellement `buildForm()` du edit dialog ; (5) ajouter le type dans `KNOWN_FRONTEND_REFERENTIAL_TYPES` (garde-fou F-225 SF-225-03). Motivation : 5 types orphelins identifiés audit 2026-05-06 (CONVENTION_PREAVIS / TRAVAIL_PROCEDURE_JALONS / FAMILLE_PROCEDURE_JALONS / MAJEURS_PROTEGES_REGIMES / IM21_VALIDITY_CRITERES). |
| 32 | Composant décisionnel frontend (`<app-XXX-section>` intégré au panel F-IA-04 via `TOOL_REGISTRY`) **sans référence explicite au template canonique** dans la mini-spec | REFUS — chaque nouveau composant décisionnel doit nommer le composant de référence (`immigration-title-decision-section` post-SF-177-12) et avoir passé la checklist du skill `ai-skills/frontend-coherence-audit.md` (§5 + §6, 19 items). Audit obligatoire tous les 5 nouveaux composants. Motivation : F-155 rétroactif sur 6 composants fin 2026-04-24. |
| 33 | Composant décisionnel frontend **sans checklist cohérence visuelle passée** (palette / datepicker / typographie / gate pays / refresh / snackbar) | REFUS — strict : (1) palette statut navy/or/vert, rouge réservé aux alertes critiques ; (2) `<input type="date">` ou `datetime-local` — pas `MatDatepicker` ; (3) `JetBrains Mono` pour `baseJuridique` et `formule`, `Inter` pour le reste ; (4) gate `workspaceCountry` = bannière info — pas de masquage silencieux ; (5) `CaseDashboardRefreshService.triggerRefresh()` dans `next:` du POST (pattern SF-IA-02-03) ; (6) `MatSnackBar` pour les erreurs — pas d'`alert()`/`confirm()`. Pattern : `immigration-title-decision-section`. Skill : `ai-skills/frontend-coherence-audit.md` §6. |
| 34 | Composant décisionnel frontend **sans pré-remplissage IA fonctionnel** (`@Input aiData?` + `prefillFromAi()` + signals provenance + badge `auto_awesome` + handlers reset) | REFUS — **FAIL, pas WARN** : bug produit, l'outil devient « encore un formulaire ». Vérification : (1) `@Input() aiData?` typé strictement ; (2) `prefillFromAi()` dans `ngOnInit()` ET `ngOnChanges()` ; (3) signal `provenance<Field> = signal<'IA'\|null>(null)` par champ ; (4) badge `auto_awesome` « Pré-rempli depuis l'analyse » ; (5) handler `onXxxChange()` qui remet la provenance à `null` au changement manuel. Pattern : `immigration-title-decision-section.prefillFromAi()`. |
| 35 | Composant décisionnel frontend **sans validation IA au changement F-IA-03** (`coherenceAlerts` computed + `<app-coherence-popover-trigger>` + helper partagé `CoherenceAlertBuilder`) | REFUS — **FAIL, pas WARN** : bug produit, l'avocat peut saisir une valeur en contradiction avec l'IA sans alerte. Vérification : (1) `coherenceAlerts = computed<Partial<Record<FieldName, CoherenceAlert>>>()` croisant 4 sources IA (`aiData`, `procedureChecks` F-96, `aiQuestions`, `piecesManquantes`) ; (2) hiérarchie F-96 > Question IA > IA détection > Pièce manquante, source `MULTI` si convergence ; (3) directive `<app-coherence-popover-trigger>` ; (4) helper partagé obligatoire `frontend/src/app/shared/coherence-popover/coherence-alert-builder.ts` — pas de définition locale. Pattern : `immigration-title-decision-section` (`buildMotifAlert`, `buildNationaliteAlert`, `coherenceAlerts`, `alertsSummary`). |
| 36 | Composant décisionnel frontend **sans entrée `TOOL_REGISTRY` symétrique aux autres outils** (inputs IA complets, constantes `TOOL_LABEL` / `TOOL_ICON`) | REFUS — l'outil ne sera pas correctement présenté dans F-IA-04 et la validation F-IA-03 ne recevra pas les sources IA. Vérification : (1) entrée `TOOL_REGISTRY` avec `inputs: (ctx) => ({ caseFileId, workspaceCountry, aiData, procedureChecks, aiQuestions, piecesManquantes })` ; (2) constantes `TOOL_LABEL` et `TOOL_ICON` symétriques (pattern SF-177-03b/05/07) ; (3) `tool_id` dans `KNOWN_FRONTEND_TOOL_IDS` (garde-fou F-164 SF-164-01). |
| 37 | Composant décisionnel frontend **sans `static getPrefillCount(input): number`** parité stricte avec `prefillFromAi()` runtime + tests Jest (0/M/N champs) | REFUS — sans cette méthode, le panel F-IA-04 affiche un badge `auto_awesome` faux ou absent AVANT instanciation. Vérification : (1) signature `static getPrefillCount(input: { aiData?, procedureChecks?, aiQuestions?, piecesManquantes?, triggerEvents?, workspaceCountry? }): number` ; (2) **parité stricte** runtime↔static via helper partagé `<ComponentName>PrefillRules` — mêmes guards, mêmes mappings, mêmes conditions de pays ; (3) tests Jest obligatoires : 0/M/N champs. Pattern : `immigration-title-decision-section`. Garde-fou F-236 SF-236-05 (`prefill-count-integrity.spec.ts`). Motivation : audit 2026-05-10 — 79 composants sur 103 (77 %) en infraction. |
| 38 | SF frontend décisionnelle mergée sans pré-remplissage IA fonctionnel **OU** sans validation F-IA-03 au changement | REFUS — ces 2 mécanismes sont la **différenciation produit** (vs « encore un formulaire ») et l'articulation entre l'IA et les outils décisionnels. Sans pré-fill, l'avocat ressaisit ce que l'IA a déjà extrait. Sans validation F-IA-03, l'avocat peut contredire l'IA sans alerte. Toute SF qui livre un composant sans ces 2 mécanismes doit être corrigée en SF suivante immédiate avant toute nouvelle feature. Audit systématique lors des audits périodiques (règle des 5 composants). |
| 39 | Migration Liquibase ou seed qui INSERT/UPDATE dans `decision_tool_visibility_rules` (mode `visibility` ou flag) **sans audit "Impact F-166 cross-C×D" rempli dans la mini-spec** | REFUS — toute modification du registre de visibilité doit être analysée croisée Country × Domain (FR×Travail, FR×Immigration, FR×Famille, BE×Travail, BE×Immigration, BE×Famille). Vérification : (1) cellule par défaut visée (ALWAYS_ON / CONTEXTUAL / OFF) pour chaque combinaison C×D ; (2) impact concret sur le panel F-IA-04 dans chaque cellule ; (3) cohérence avec les autres outils déjà présents. Garde-fou F-199 SF-199-02. |
| 40 | Ajout d'une entrée seed `legal_referentials` ou `decision_tool_visibility_rules` avec `country='FR'` ou `country='BE'` **sans audit explicite "exhaustivité du droit national X-FR/BE" rempli dans la mini-spec** | REFUS — pour chaque entrée nationale ajoutée côté FR, l'équivalent BE doit avoir été vérifié (existe / pas pertinent — justifier) ; et inversement. Vérification : (1) source juridique nationale (Code du travail FR / Code civil FR ; Code du travail BE / Code civil BE / régimes Bruxelles-Wallonie-Flandre) ; (2) équivalent dans l'autre pays — entrée jumelle simultanée OU justification explicite ; (3) cohérence terminologique. Couvre l'invariant "Belgique never forget". Garde-fou F-199 SF-199-02. |
| 41 | Composant Angular décisionnel frontend (entrée `TOOL_REGISTRY`) sans `static getPrefillCount(input): number` exposé OU avec `getPrefillCount` retournant NaN/Infinity/négatif | REFUS — l'avocat ne verra pas le badge `auto_awesome (+N)` du panel F-IA-04, ce qui invalide la promesse UX « outils décisionnels assistés par l'IA ». Vérification : (1) méthode statique exposée ; (2) reproduit fidèlement `prefillFromAi()` runtime via helper partagé `<ComponentName>PrefillRules` ; (3) testée Jest dans 3 cas (0/M/N champs). Le test `prefill-count-integrity.spec.ts` échoue automatiquement en CI. Garde-fou F-236 SF-236-05. |
